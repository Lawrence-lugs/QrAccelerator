- **Decision point.** The choice changes what gets built, moved, deleted, committed, or published. Ask.
- **Build or buy.** The work could be implemented by the project itself or by a library or tool. Ask which one, and name the candidates.
- **Ambiguous spec.** The user's words could mean more than one thing. List the readings as options and ask which one. Do not pick silently.
- **Irreversible or external action.** Pushes, force operations, deletions, large file moves, paid services, and changes to CI or shared infrastructure. Ask.

Rules for asking:

- Batch related questions into one `question` call. Each question has a short header, a full question, and concrete options. Put the recommended option first with "(Recommended)" in its label.
- Each answer becomes a decision in the plan, marked "DECISION (from user)". Do not carry unanswered questions into "fixed" decisions; keep them as ASK USER items with a default.
- If the `question` tool is not available, list the same questions in section 3 of the plan as Q-items, each with a default, and tell the user in the final reply.

## Plan file structure (required, in this order)

### Title and header

- Title line: `# <Project> <goal> plan`.
- Repo path, branch, HEAD hash, license if relevant.
- Plan file path and execution scratchpad path (absolute Windows paths).

### 0. Ground rules for the executing agent (READ FIRST)

Numbered rules `0.1`, `0.2`, ... Include at least:

- 0.1 Read the whole plan once. At the start of every session and after every step, re-read the execution scratchpad. Never work from memory.
- Shell rules. Name the shell (for example PowerShell). State the command separator (`;` in PowerShell, never `&&` unless verified). Forbid `echo "===";` style separators.
- Host tools. List what is on PATH, what is missing, and which steps must run inside a container or other environment. Say explicitly which tools are NOT available, so the executor does not try them.
- Git rules. Name the branch to create. Forbid history rewrite (`rebase`, `filter-repo`, `commit --amend` on existing commits, `push --force`, `reset --hard` on tracked work). Say whether push is allowed.
- Submodules and vendored content: name the path and whether it may be touched. Name the one allowed submodule command, if any.
- Every step has an **ACCEPT** line. A step is done only when its ACCEPT check passed. Record the result in the scratchpad.
- Deviation rule: if reality differs from the plan, write a DEVIATION entry, choose the smallest reasonable fix, continue. Stop and ask the user only for items marked **ASK USER**.
- Code comments: match surrounding density. Do not add comments that narrate changes (for example "removed X", "added for Y", "fixed bug"). Comments explain non-obvious behavior only.
- Destructive-action rule (see section 0a below).

### 0a. Guardrails: scope and untouchables (REQUIRED)

A weak executor drifts. Prevent it explicitly:

- **Scope statement**: one paragraph saying what is in scope and what is out of scope.
- **Untouchables list**: explicit paths and content that must not change. Include generated data, thesis or frozen results, proprietary files, submodules, and anything the user said to keep. Use exact paths, not patterns, where possible.
- **Allowed-to-change list**: the files each phase may modify. Anything not listed needs a DEVIATION entry before touching it.
- **Deletion rule**: never use `rm`, `Remove-Item`, or `git rm` for files that are not explicitly named as deletion targets. Instead move them with `mv` (or `git mv` for tracked files) to a holding location: a designated archive folder in the repo, or the temp folder `C:\Users\lafqu\AppData\Local\Temp\opencode\` for scratch items. Record every move in the scratchpad.
- **No silent improvisation**: do not rename, reformat, or refactor files that the plan does not mention.
- **Do not change test semantics** when fixing tests unless the step says so.
- **Ask-user gates**: list every decision point as an ASK USER item with a default. The executor proceeds with the default only if the user does not answer, and records it.

Rules for the scratchpad:

- The TODO list is copied from the plan's step list, one line per step ID, same order. The executor may add lines for sub-steps it creates, but may not remove plan steps. Added lines are marked `(added)`.
- The executor may update the TODO list when a step splits or becomes unnecessary, but each change needs a DEVIATION entry.
- A reader must be able to catch up from the EVOLUTION LOG and DEVIATIONS alone. Keep those entries one line each.

ACCEPT for P0.1 (always include): the scratchpad file exists and its TODO list contains every step ID.

### 2. Background facts

A verified fact list. Each fact names the source file and line or command. Include:

- Repo facts that affect execution (file counts, which files are tracked and why, generated files).
- Known bugs with exact file and line.
- CI or environment failures, with what evidence exists and what is no longer recoverable.
- Naming traps that must NOT be changed (for example a misspelled identifier used across files).

Mark anything unverified as UNVERIFIED.

### 3. Open questions

`Q1`, `Q2`, ... Each has: the question, the phase it blocks (ASK USER before step X), and the default if the user does not answer. Put "Default: NO" or a concrete default for every question.

### 4. Phases

Phases are numbered `P0`, `P1`, ... Start with P0 (baseline and safety), which always:

- Creates the scratchpad (P0.1, ACCEPT: file exists with TODO list).
- Creates the branch from the stated base and checks the tree is clean (P0.2). Expect a clean tree, or stop and ask the user.
- Records baseline numbers (file counts, hashes, failing checks) in the scratchpad.
- Commit: none.

Structure rules for every phase:

- **Goal line**: one sentence on what the phase achieves.
- **Steps**: IDs `Px.y`. Each step has exact commands or exact edit instructions, and the exact file path and line or search anchor. Give the executor the exact text to write when the change is small. For larger changes, give the exact content of the new file.
- **ACCEPT line** on every step: a runnable check with an expected result (exit code, string present, file exists, count). No vague ACCEPT such as "works".
- **Decisions already made**: write them as "DECISION (fixed; do not redesign)". Never leave a design choice to the executor unless it is an ASK USER item.
- **Failure path**: say what to do if an ACCEPT fails (record, go to a named diagnostic step, or ASK USER).
- **Commit line**: at the end of every phase, a `Commit Px:` line with the exact message, or `Commit: none` with a reason. Commit once per phase, not per step. Use `git add` on the named files only, never `git add -A`, unless the phase says so.

Branching and phasing rules:

- Work happens on one new branch created in P0. Never commit to the base branch.
- One commit per phase (a phase may be split into a/b commits only if the plan says so).
- Each phase ends with its commit. Before starting the next phase, the executor confirms the previous phase's ACCEPT checks and commit are recorded in the scratchpad.
- Diagnostic phases (investigating a failure) come before cleanup phases.
- Documentation comes after code changes that it describes.
- Verification (full checks, inside any container) is its own final phase.

Anticipate the executor's difficulties and write the answer into the step:

- Quoting and escaping for the chosen shell (paths with spaces, `$` in strings, quoting regex in `Select-String`).
- Commands that print a lot: say to use `Select-Object -First N` or redirect to a file.
- Long-running commands (builds, image pulls): state expected duration and where to save the log.
- Line-number drift: give a search anchor as well as a line number, and say to re-locate by anchor if the line differs.
- Tools that look present but are not (for example a Python stub): state the real working command.

### Final phase: Verification and critique

The last two phases are always:

- **Verification phase (Pn)**: re-run all ACCEPT-level checks that matter for the whole goal, record exit codes, and list anything skipped with its reason.
- **Critique phase (Pn+1)**: after the executor finishes all phases, it spawns a critique subagent and addresses its findings.

Write the critique phase exactly like this:

```
P<n+1>.1 Spawn a critique subagent with the subagent tool (agent "general", description "critique executed plan"). Prompt it with:
- the absolute plan path and execution scratchpad path,
- the branch name and base hash,
- the instruction: "Review the executed work against the plan. Check each ACCEPT line was truly satisfied, look for untouchable violations, unrecorded deviations, missing moves, comment-density or narrating-comment problems, and anything that was skipped without a reason. Do not edit files. Return a numbered list of findings, each with severity (blocker, major, minor), evidence (file and line or command output), and a suggested fix."
P<n+1>.2 For each finding: fix it if it is a blocker or major, or if the fix is small and inside the allowed-to-change list. Otherwise record it as OPEN with a reason. Record every finding and its disposition in the scratchpad (new section "## CRITIQUE FINDINGS").
P<n+1>.3 Re-run the affected ACCEPT checks. Commit the fixes as "critique fixes" on the same branch, using a single commit, only if any files changed.
ACCEPT: every finding has a disposition; no blocker is OPEN.
```

Add a `## CRITIQUE FINDINGS` section to the scratchpad template when the plan uses the critique phase (it always does).

Finally, the plan ends with a handover step (P<n+2>): write a report file next to the plan, listing per-phase summary, commit hashes (`git log --oneline <base>..<branch>`), verification results, deviations, and open questions, and check no unchecked TODO box lacks a reason.

### Definition of done

A numbered list of observable outcomes. Each item maps to a phase or check. The executor must be able to say yes or no to each item.
